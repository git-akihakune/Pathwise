# Pathwise v1 · Plan 1: Foundation Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A deployable, authenticated, otherwise empty Pathwise shell. A fresh clone plus `docker compose up` yields a working instance where the first sign-up becomes admin, and the admin can manage sign-up mode and invites.

**Architecture:** A pnpm monorepo with `packages/core` (config, DB, auth, services; no Next.js imports), `apps/worker` (one Node bundle serving the `init`, `worker`, and `pathwise` CLI entrypoints), and `apps/web` (Next.js 16, a thin adapter over core). A single multi-stage Docker image runs all three. Compose wires `postgres` → one-shot `init` → `web` + `worker`.

**Tech Stack:** Node 24, pnpm 12, TypeScript 6, Next.js 16.4, React 19, Tailwind 4 + shadcn/ui, Drizzle ORM 0.45 + drizzle-kit 0.31, node-postgres, Better Auth 1.7 (admin plugin), pg-boss 12, Zod 4, pino, Vitest 5 + Testcontainers, Playwright, Biome 2, esbuild, Docker Compose v2.

**Spec:** [docs/superpowers/specs/2026-10-12-pathwise-design.md](../specs/2026-10-12-pathwise-design.md). This plan implements §4.1–4.3, §4.5, the identity/instance parts of §6.1, and the auth parts of §10.

## Global Constraints

- Node `>=24`; pnpm `12.11.2` pinned via `packageManager`; all packages `"type": "module"`.
- TypeScript `~6.0.3`, `strict: true`, `moduleResolution: "bundler"`. Not TS 7: the native compiler's tooling compatibility with Next.js and drizzle-kit is unverified.
- Versions: next `16.4.x`, react `19.3.x`, drizzle-orm `0.45.x`, drizzle-kit `0.31.x`, better-auth `1.7.x`, pg-boss `12.x`, zod `4.x`, tailwindcss `4.x`, vitest `5.x`, @playwright/test `1.64.x`, @biomejs/biome `2.x`.
- `packages/core` must never import `next` or any `next/*` module.
- User and instance data is read or written only via `packages/core` functions. Web code never builds queries.
- Admin-only core functions take an `actorId` and enforce the role server-side (spec §10).
- Every configuration value is optional with a safe default, except `DATABASE_URL`, which compose always provides (spec §4.5). An empty-string env var counts as unset.
- `init` must be idempotent and must not use the network beyond Postgres (spec §4.5).
- The first registered user becomes admin. After that, `signup_mode` defaults to `invite_only` (spec §10).
- Minimum password length: 12.
- Secrets `APP_ENCRYPTION_KEY` and `BETTER_AUTH_SECRET`: env var if set, else `${SECRETS_DIR}/<NAME>`, generated by `init` (32 random bytes, base64, mode 0600) (spec §4.5).
- Default paths: `SECRETS_DIR=/var/lib/pathwise/secrets`, `FILES_DIR=/var/lib/pathwise/files`.
- Postgres port is never published by `compose.yaml`; the image runs as a non-root user.
- License: AGPL-3.0.

## Review Focus

These are the five failure modes most likely to bite a real user. Each has a test in the task that owns the code:

1. **Two people submit the bootstrap sign-up at the same moment** → exactly one becomes admin; the other is told sign-up needs an invite. (Task 5)
2. **Instance opened at a different origin than `APP_URL`** (e.g. `http://192.168.1.20:3000` on a LAN server while `APP_URL` is the default `localhost`) → Better Auth rejects the request as untrusted; the user must see an explanation naming `APP_URL`, not a silent failure. (Task 9)
3. **Email case differences** (invite for `Alice@Example.com`, sign-up as `alice@example.com`; later a duplicate as `ALICE@example.com`) → the invite is accepted; the duplicate is rejected as "email taken". (Tasks 4 and 5)
4. **A secret file exists but is corrupt** (truncated, wrong length, edited by hand) → `init` fails loudly and never overwrites it, because overwriting would make every stored API key undecryptable. (Task 2)
5. **A used, expired, revoked, or mistyped invite link is opened** → a friendly page explaining which, never a 500 or a sign-up form that fails on submit. (Task 10)
